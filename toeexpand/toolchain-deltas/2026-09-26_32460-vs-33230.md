# Toolchain delta: TouchDesigner 2025.32460 → 2025.33230

## Summary

Across 1,813 total inputs (golden repo set, `CurriculumExamples`, and the full
shipped-`tfs` OPSnippet corpora of both builds), `toeexpand`/`toecollapse`
behaviour is unchanged between 2025.32460 and 2025.33230: expand trees,
collapse bytes, and fixed-point convergence are all identical build-to-build,
even though the wrapper binaries *and* their backing dylibs both changed.
The `tocdir` parser/census sees no new file kinds and no new unparsed kinds
in the new build's shipped corpus, but does see one new `.parm` mode bit
(`0x1000`, saved by TD itself rather than produced by the toolchain) and a
handful of genuinely new operator types with shipped snippets.

**Determinism control:** repeated runs of the same toolchain build against
the same input are byte-identical on both 2025.32460 and 2025.33230 (W2),
which rules out run-to-run non-determinism as an explanation for any
diff anywhere in this sweep.

**Harness validation:** running the *old* 2025.32460 binary over the old-tfs
fileset reproduces the previously-committed 2026-06-01 shipped-corpus
manifests (`toeexpand/resources/shipped/`) 788/788 (the 8 `.toe` files in
the old-tfs set aren't part of that corpus, so they're excluded from this
check). This confirms the harness itself — not just its internal
self-consistency — before trusting the A/B comparisons above.

**Forward compat:** the new-tfs comparison (804/804 identical) means the
*old* 2025.32460 toolchain parses/round-trips every file newly introduced or
re-saved by 2025.33230 — new operator snippets, the new `.parm` mode bit
included — exactly as the new toolchain does. Nothing in this update
required a newer parser to read what it produced.

**`collapse(expand(x)) == x`:** only true when `x` was itself produced by
`toecollapse` (`td-snapshot.tox`, both builds). Every TD-*saved* `.tox`/`.toe`
in the sweep (13 golden fixtures + 199 curriculum files) differs from its
own re-collapsed bytes on the first round, but reaches a fixed point after
exactly one expand/collapse round on both builds — `toecollapse`'s output is
a canonical re-framing of TD's save format, not a reproduction of it.

## Pinned quirks (identical on both builds)

- **Exit codes are inverted from convention:** `toeexpand` returns `rc=1` on
  a fully successful expansion and `rc=0` on failure (missing input, or the
  target `.dir` already existing). Judge success by whether `.dir/` was
  produced, never by exit code.
- **`-b` reports the *file's* `.build` stamp, not the toolchain's own build.**
  Given a `.tox` saved by a different TD version than the running toolchain,
  `-b` prints that file's embedded version/build/osname/osversion/time —
  useful for provenance, useless for asking "what toolchain am I running."
- **The `pattern` argument is effectively broken on both builds:**
  `toeexpand <file> <pattern>` writes the full `.toc` index but never
  produces the corresponding `.dir/` tree — the filtered-expansion feature
  doesn't do anything observable beyond the unfiltered case's `.toc` write.
- **Expanding into an existing `.dir` is a silent no-op:** exit code 0,
  stderr says the directory "already exists", and the tree on disk is left
  untouched (not merged, not refreshed).
- **`.toe` collapse output is reproducibly larger than the original**, e.g.
  3418 → 3426 bytes on one golden sample — the framing diverges right after
  the `10\0\0` magic, consistent with the pre-existing "canonicalization, not
  drift" finding in `toeexpand/FORMAT.md`'s case-collision section. Both
  builds diverge from the original input by the same amount and converge to
  the same fixed point.

## Question B — new operators & structures

**New operator types.** The shipped-OPSnippets inventory grew by 8 files
(788 → 796 `.tox`): `gltfinCOMP`, `gltfoutCOMP`, `scriptPOP`, `timefilterPOP`,
a new `layermixTOP` snippet, and three GaussianSplats snippets
(`gsGeo`, `gsScene`, `gsTransform`). Of these, the census's
`operator_types` set (`FAMILY:type` strings actually seen in a `.n` file)
gained exactly five new entries: `COMP:gltfin`, `COMP:gltfout`, `POP:script`,
`POP:timefilter`, `TOP:layermix` (565 → 570 types). **`layermixTOP`'s
snippet is new but the TOP itself is not** — `layermix` already existed as
an operator prior to this build; only now does a shipped snippet exercise
it, which is why it shows up as a "new" census entry despite not being a new
op. The three GaussianSplats snippet files do **not** add new
`FAMILY:type` entries to the census at all — consistent with them being
`COMP:base`-wrapper stub components (the same pattern FORMAT.md already
documents for the `cplusplus*` snippets), not new native operator types.

**Census comparison, shipped corpus (32460: 788 trees / 33230: 796 trees):**
no new file kinds, same 31 `unparsed_kinds`, same `.toc` header
(`# 4 0 0 0 1` on all trees, both builds), same `.build` app_version `099`
on the vast majority of trees (2 legacy `077` trees carried over unchanged),
and the same `.n` flag-token vocabulary (21 tokens, unchanged).

**`.parm` mode vocabulary delta:** 151 → 152 distinct mode values
(net +1: two new values appear, one disappears):

- **`+4096` (`0x1000`) — new bit, see below.**
- **`+262161` (`0x40011`)** — one occurrence in the shipped-corpus census
  diff (no specific parameter identified in this pass). `0x40000` is already
  a common high-bit combination in the existing vocabulary (custom-page /
  OP-typed family); `0x40011` = `0x40000 | 0x11`, i.e. the already-documented
  low-byte expression pattern (`0x11`) combined with a bit that was already
  attested elsewhere, just not previously seen paired with `0x11`. Not a new
  bit — a new *combination*. (Don't confuse with `patternPOP.attrnumcomps`
  below, which is a *different* mode — `0x1011`, i.e. `0x1000|0x11`.)
- **`-201327155` removed** — `0x0C000033` no longer appears; it previously
  showed up on `camSchnappr`'s `point2diffr`/`g`/`b` and on removed
  `SOP:vertex`/`SOP:point` parameters. This tracks a snippet content change
  (parameters dropped from the snippet), not a toolchain/format change.

### The `0x1000` finding, in detail

**Evidence:** `parm_vocab.modes["4096"]` is absent from the 2025.32460
census and present (count 7) in the 2025.33230 census. All 7 occurrences
are on parameters that were also present (at mode 0) in the corpus prior
to this build:

- `randomPOP`'s `attr*` parameters — this snippet's `.build` stamp shows it
  was re-saved at build **2025.33181** (between the two toolchains under
  test), so this occurrence predates 2025.33230's release but postdates
  2025.32460.
- In the `every_op` fixture generated fresh at 2025.33230 (via the TD
  bridge, not from a shipped snippet): **every 3D COMP type**
  (`geometry`, `actor`, `blend`, `bone`, `bulletsolver` and its actors,
  `constraint`, `fbx` and its children, `force`, …) stores
  `instancetexextendu`/`v`/`w`, `instancetexfilter`, and
  `instancetexanisotropy` with mode `4096`, **at their default values**
  (`repeat` / `mipmaplinear` / `off`); `patternPOP`'s `attrnumcomps` shows
  the same bit combined with the expression flag — mode `4113` (`0x1011` =
  `0x1000|0x11`), value/expr `1 me.par.vecsize`.

**Hypothesis (unconfirmed):** `0x1000` marks a parameter value that TD wrote
out even though it equals a computed/dynamic default, rather than a true
"changed from default" value — i.e. it's a "written but not overridden"
flag distinct from the existing "has expression" (`0x30`) bits. This is
consistent with it appearing on a whole cluster of texture-extend/filter
pars that are always present on 3D COMPs regardless of whether the user
touched them.

**What's confirmed:** both toolchains pass the bit through byte-identically
(no toolchain-side interpretation); `tocdir`'s `.parm` parser round-trips it
correctly since it treats mode as an opaque integer; `has_expression`
(`mode & 0x30`) is unaffected — `0x1000` doesn't overlap the existing
expression bits. The old (≤2025.32424) shipped corpus never shows this bit;
those same `instancetex*` parameters, when they appear at all in the old
corpus, are mode `0`.

**Suggested confirmation step (not done in this pass):** generate the
`every_op` fixture in TD 2025.32460 itself (mount the DMG, launch the app,
run the generator) and diff its `.parm` modes against the 2025.33230
`every_op` fixture already committed. That isolates whether `0x1000` was
introduced somewhere in (2025.32460, 2025.33181] — narrowing past the
single re-saved `randomPOP` data point currently available — or is itself
new exactly at 2025.33230.

### Parameter-name deltas in `type_pars`

**Caveat:** `.parm` only stores *non-default* parameters, so any snippet
re-save that changes a parameter's stored value away from (or back to) its
default will change what shows up in `type_pars`, independent of whether TD
actually added/removed a parameter definition. These are reported as
observed deltas, not confirmed schema changes:

- **`MAT:pbr`** — new names present in 2025.33230 include
  `basecolormapextendu`/`v`, `emitmapextendu`/`v`, `normalmapextendu`/`v`,
  `metallicmapextendu`/`v` (+`metallicmapchannelsource`),
  `roughnessmapextendu`/`v` (+`roughnessmapchannelsource`), plus `blending`
  and `cullface`. Reads as the PBR snippet's saved state now diverging from
  default on the texture-extend/channel-source family of pars (plausibly
  related to the same texture-extend surface the `0x1000` bit touches).
- **`POP:glsl`** — 2025.33230 shows many additional `matattr0/1*` and
  `vec1..vec4*` names (`matattr0name`, `matattr0numcols`, `vec1valuex`, …)
  that 2025.32460 doesn't. Reads as the snippet exercising more of the
  attribute-array UI (`attr0arraysize`, `attr0isarray`) than the old
  snippet did, not a new parameter surface in the operator itself.
- **`TOP:moviefileout`** — 2025.33230 drops `bitratemode`, `preset`,
  `videopixelformat` from the non-default set and adds `qualitymode`,
  `qualityscale`, `ratecontrolmode`, `pageindex`. Reads as the snippet's
  encoder settings being re-saved with a different set of non-default
  choices (e.g. quality-based rate control instead of bitrate/preset), not
  necessarily a change to the parameter template itself.
